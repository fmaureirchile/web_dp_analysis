Roadmap de desarrollo
Plataforma de descubrimiento y evaluación de captura de datos personales en aplicaciones web
Versión:0.1Objetivo:establecer una secuencia de construcción coherente, posteriormente descomponible en épicas, historias y tareas pequeñas para desarrollo asistido mediante vibe coding.
1. Principio rector del roadmap
El producto deberá desarrollarse desde el núcleo hacia las capacidades especializadas, siguiendo esta progresión:
Autorización y alcance        ↓Modelo común de datos y evidencias        ↓Exploración externa pasiva        ↓Observación dinámica del navegador        ↓Clasificación de datos        ↓Análisis de consentimiento        ↓Revisión y reportes        ↓Evaluación autenticada        ↓Análisis de código y sistemas internos        ↓Linaje integral        ↓Monitoreo continuo
La regla principal será:
Ninguna fase deberá crear una estructura paralela para representar datos, evidencias, ejecuciones o hallazgos.
Todas las capacidades deberán utilizar el mismo modelo de dominio, repositorio de evidencias, mecanismo de clasificación y proceso de revisión.
La plataforma entregará evidencia técnica y documental, pero no determinará automáticamente la licitud jurídica definitiva del tratamiento. La Ley N.º 21.719 exige considerar finalidad, proporcionalidad, transparencia, base de licitud y consentimiento cuando corresponda.
2. Estrategia general de construcción
2.1 Construcción mediante cortes verticales
No se recomienda desarrollar primero toda la interfaz, luego todo el backend y finalmente los escáneres.
Cada incremento deberá recorrer una funcionalidad completa:
Configuración    ↓Ejecución    ↓Captura    ↓Persistencia    ↓Clasificación    ↓Evidencia    ↓Visualización    ↓Prueba automatizada
Ejemplo de primer corte vertical:
Ingresar una URL, ejecutar una exploración de una sola página, detectar un formulario, guardar sus campos y mostrarlos en pantalla con una captura de evidencia.
Este enfoque permite probar tempranamente que la arquitectura es funcional.
2.2 Modularidad progresiva
La primera versión debe construirse como unmonolito modular con workers desacoplados, evitando microservicios prematuros.
Separación lógica inicial:
Portal web.
API de gestión.
Orquestador.
Worker de crawling.
Worker de navegador.
Motor de clasificación.
Repositorio de evidencias.
Generador de reportes.
Los módulos podrán separarse físicamente más adelante cuando existan razones operacionales reales.
2.3 Contratos antes que implementación
Antes de programar cada fase deberán definirse:

El vibe coding deberá implementar contratos previamente establecidos, no inventarlos durante cada tarea.

7. Camino crítico
La secuencia mínima obligatoria será:
Etapa 0→ Etapa 1→ Etapa 2→ Etapa 3→ Etapa 4→ Etapa 5→ Etapa 6→ Etapa 7→ Etapa 8→ Etapa 9→ Etapa 10
No deberá desarrollarse:
Consentimiento antes del navegador automatizado.
Linaje antes del modelo de evidencia.
Análisis backend antes de estabilizar la taxonomía.
Monitoreo continuo antes de contar con resultados reproducibles.
IA generativa antes de disponer de reglas determinísticas y corpus de evaluación.
Las etapas 12 y 13 podrán avanzar parcialmente en paralelo, una vez estabilizados el modelo de dominio y el repositorio de evidencia.
8. Reglas para descomponer el roadmap en vibe coding
Cada tarea entregada a un agente de código deberá contener:
8.1 Objetivo único
Ejemplo:
Implementar la entidadFormFieldy sus migraciones.
No:
Implementar el módulo de formularios completo.
8.2 Contexto explícito
Fase.
Módulo.
Entidades relacionadas.
Contratos existentes.
ADR aplicables.
8.3 Archivos permitidos
Se deberá indicar qué carpetas puede modificar el agente.
8.4 Archivos prohibidos
Especialmente:
Migraciones anteriores.
Contratos publicados.
Configuración de seguridad.
Módulos fuera del alcance.
8.5 Entradas y salidas
Payload.
Respuesta.
Errores.
Eventos.
Estados.
8.6 Criterios de aceptación verificables
Ejemplo:
Crea una migración.
Agrega pruebas.
No rompe contratos anteriores.
El lint pasa.
La API aparece en OpenAPI.
8.7 Pruebas obligatorias
Unitarias.
Integración.
Regresión.
Sitio sintético cuando corresponda.
8.8 Restricciones
No crear dependencias nuevas sin autorización.
No cambiar el modelo de dominio.
No duplicar utilidades.
No guardar secretos.
No desactivar pruebas.
No utilizaranysalvo excepción justificada.
No modificar contratos sin ADR.
9. Tamaño recomendado de las tareas
Para vibe coding, cada tarea debería representar entre medio día y dos días de trabajo humano equivalente.
Ejemplos adecuados:
Crear normalizador de URLs.
Detectar campos obligatorios.
Persistir screenshot.
Capturar LocalStorage.
Enmascarar encabezado Authorization.
Comparar cookies entre dos sesiones.
Agregar revisión manual de una clasificación.
Exportar inventario a CSV.
Ejemplos demasiado grandes:
Construir el crawler.
Implementar consentimiento.
Crear análisis de código.
Implementar reportes.
Hacer la plataforma segura.
Las funcionalidades grandes deberán dividirse por comportamiento observable.
10. Definition of Ready
Una tarea estará lista para vibe coding sólo cuando tenga:
Objetivo.
Dependencias.
Contrato.
Modelo de datos.
Casos de prueba.
Criterios de aceptación.
Archivos afectados.
Restricciones.
Ejemplo de entrada.
Ejemplo de salida.
11. Definition of Done
Una tarea se considerará terminada cuando:
El código compile.
El lint pase.
Las pruebas pasen.
Existan pruebas nuevas.
No existan secretos.
Las migraciones sean reversibles.
La documentación esté actualizada.
OpenAPI esté actualizado.
La funcionalidad esté observable.
Los errores estén controlados.
No se rompa el corpus dorado.
El código haya sido revisado.
El resultado corresponda exactamente al alcance de la tarea.
12. Mecanismos para mantener coherencia
12.1 Modelo de dominio único
Las entidades centrales vivirán en un paquete compartido y no deberán duplicarse.
12.2 API versionada
Toda integración utilizará contratos definidos.
12.3 Migraciones obligatorias
No se permitirán cambios manuales de esquema.
12.4 Eventos normalizados
Ejemplos:
execution.created
execution.started
page.discovered
form.detected
data.observed
evidence.created
finding.confirmed
execution.completed
12.5 Correlation ID
Toda ejecución, sesión, solicitud y evidencia deberá estar correlacionada.
12.6 Versionamiento de clasificadores
Cada clasificación deberá registrar la versión de reglas o modelo.
12.7 Pruebas doradas
Los resultados esperados del laboratorio deberán almacenarse y compararse automáticamente.
12.8 Feature flags
Las capacidades experimentales deberán activarse por configuración.
12.9 Revisión arquitectónica
Todo cambio que afecte más de un módulo requerirá ADR o revisión explícita.
12.10 Evitar correcciones locales
Cuando una tarea revele una limitación del modelo común, deberá corregirse el modelo central y no introducir excepciones ocultas en un módulo.
13. Riesgos principales del desarrollo con vibe coding
Fragmentación del modelo
Distintos agentes pueden crear estructuras equivalentes con nombres diferentes.
Mitigación:contratos y paquete de dominio único.
Sobreingeniería
La IA puede incorporar patrones innecesarios.
Mitigación:monolito modular y dependencias controladas.
Funcionalidades sin pruebas
La generación rápida puede producir componentes aparentemente terminados.
Mitigación:ninguna tarea se cierra sin pruebas.
Pérdida de seguridad
Los agentes pueden registrar tokens, cuerpos completos o credenciales.
Mitigación:librería central de redacción y pruebas de no exposición.
Cambios incompatibles
Una tarea puede modificar contratos utilizados por otras fases.
Mitigación:API versionada, migraciones y pruebas de contrato.
Falsos positivos crecientes
La incorporación rápida de reglas puede reducir la precisión.
Mitigación:corpus dorado, métricas y revisión humana.
Dependencia excesiva de IA generativa
La IA puede entregar conclusiones difíciles de reproducir.
Mitigación:reglas determinísticas primero, IA como apoyo y evidencia explicable.
14. Primer hito funcional recomendado
El primer hito demostrable no debería ser un dashboard general.
Debería ser este flujo completo:
Crear proyecto.
Registrar autorización.
Ingresar una URL.
Validar alcance.
Visitar una página.
Detectar un formulario.
Detectar sus campos.
Clasificar nombre y correo.
Capturar screenshot.
Guardar evidencia.
Mostrar resultados.
Exportar CSV.
Ejecutar pruebas contra un sitio sintético.
Este hito validará:
Arquitectura.
Modelo de dominio.
Orquestación.
Persistencia.
Evidencia.
Clasificación.
Interfaz.
Reportería.
Seguridad de alcance.
15. Segundo hito funcional recomendado
El segundo hito deberá demostrar la capacidad diferenciadora:
Abrir un sitio con banner.
Ejecutar una sesión sin interacción.
Ejecutar otra sesión rechazando.
Ejecutar otra aceptando.
Capturar cookies y tráfico.
Comparar resultados.
Mostrar diferencias.
Generar un hallazgo revisable.
Vincularlo con evidencia.
Exportar un reporte.
Este hito materializa la principal propuesta de valor del producto.
16. Resultado esperado del roadmap
Al completar las etapas, la plataforma deberá poder responder, con distintos niveles de evidencia:
Qué datos solicita un sitio.
Qué datos genera automáticamente.
Qué datos guarda en el navegador.
Qué datos transmite.
A qué dominios los transmite.
En qué estado de consentimiento ocurre.
Qué información se muestra al usuario.
Qué código participa en la captura.
Dónde se procesa o almacena.
Qué diferencias existen entre lo declarado y lo observado.
Qué elementos requieren revisión humana.
La secuencia propuesta permite que cada release sea utilizable por sí sola, pero que sus resultados sigan alimentando el mismo modelo de datos y evidencia, evitando reconstrucciones profundas en las fases posteriores.
