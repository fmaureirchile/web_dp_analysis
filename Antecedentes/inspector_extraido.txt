Especificación de requerimientos
Plataforma de descubrimiento y evaluación de captura de datos personales en sitios y aplicaciones web
Nombre provisional:Web Data Discovery & Consent InspectorVersión:0.1Marco principal:Ley chilena N.º 21.719Ámbito:Sitios públicos, portales privados, extranets, intranets, aplicaciones web y APIs asociadas.
1. Antecedentes
La Ley N.º 21.719 considera dato personal cualquier información vinculada o referida a una persona natural identificada o identificable. Asimismo, entiende por tratamiento cualquier operación que permita recolectar, procesar, almacenar, comunicar, transmitir o utilizar datos personales.
Desde la perspectiva de una aplicación web, la captura de datos puede producirse mediante:
Formularios visibles.
Campos ocultos.
Parámetros en URL.
Cookies.
Identificadores de sesión.
Datos del navegador o dispositivo.
Dirección IP.
Geolocalización.
Scripts de analítica o publicidad.
Chatbots.
Carga de archivos.
APIs.
Eventos de interacción.
Logs técnicos.
Integraciones con terceros.
Datos inferidos o perfiles generados a partir de la conducta del usuario.
La ley exige que los datos se recolecten con fines específicos, explícitos y lícitos; que se limiten a aquellos necesarios, adecuados y pertinentes; y que el responsable pueda acreditar la licitud del tratamiento. También exige transparencia respecto de los datos tratados, sus finalidades, bases de licitud, destinatarios, conservación, transferencias y decisiones automatizadas.
Cuando se utilice el consentimiento como fundamento, este debe ser libre, informado, específico, previo e inequívoco, expresado mediante una acción afirmativa. El responsable debe ser capaz de acreditar que obtuvo dicho consentimiento.
2. Propósito del sistema
El sistema tendrá como propósito:
Descubrir, clasificar, documentar y correlacionar los datos personales que una aplicación web solicita, genera, almacena o transmite, junto con la evidencia observable de información, consentimiento o autorización presentada al usuario.
La plataforma deberá funcionar en distintos niveles de profundidad, desde una evaluación externa no autenticada hasta una revisión interna autorizada de código fuente, APIs, bases de datos, configuraciones e infraestructura.
3. Principio fundamental de la solución
El software deberá distinguir claramente entre:
3.1 Hechos técnicamente observados
Por ejemplo:
El formulario solicita un RUT.
La página registra una cookie.
El navegador transmite una dirección de correo a una API.
Un píxel de terceros se ejecuta antes de aceptar cookies.
Una librería almacena un identificador enlocalStorage.
Un endpoint recibe nombre, correo y teléfono.
El backend guarda esos datos en una tabla.
El código envía información a una plataforma externa.
3.2 Evidencia de información o consentimiento
Por ejemplo:
Existe una casilla de consentimiento.
La casilla se encuentra premarcada.
El sitio muestra una política de privacidad.
El texto menciona la finalidad.
El consentimiento es general o específico.
El usuario puede rechazar cookies.
Las etiquetas de analítica se ejecutan antes o después de la elección.
Existe una función para retirar el consentimiento.
Se registra la versión del texto aceptado.
3.3 Conclusión jurídica
La plataformano deberá afirmar automáticamenteque un tratamiento es legal o ilegal.
Deberá emitir conclusiones limitadas, tales como:
“No se observó evidencia de información previa”.
“El dato fue transmitido antes de que el usuario realizara una acción afirmativa”.
“Se detectó una solicitud de consentimiento”.
“La finalidad no fue encontrada en el texto analizado”.
“Existe una posible discrepancia entre el comportamiento técnico y la política publicada”.
“La base de licitud no puede determinarse mediante observación externa”.
“Se requiere validación jurídica y operacional”.
La licitud puede fundarse en consentimiento, ejecución contractual, obligación legal, interés legítimo u otra fuente reconocida por la ley. Por eso, la ausencia de una casilla de consentimiento no implica necesariamente que el tratamiento sea ilícito.
4. Objetivos específicos
El sistema deberá permitir:
Identificar los puntos de captura de datos de una aplicación web.
Clasificar los datos encontrados conforme a una taxonomía legal y técnica.
Observar datos capturados automáticamente por el navegador.
detectar transmisiones hacia APIs propias y de terceros.
Analizar cookies, almacenamiento local, sesiones e IndexedDB.
Detectar formularios, campos visibles y campos ocultos.
Detectar elementos de información y consentimiento.
Comparar el comportamiento antes y después de aceptar o rechazar.
Identificar discrepancias entre políticas declaradas y comportamiento observado.
Analizar código fuente frontend y backend cuando exista autorización.
Construir trazabilidad desde la interfaz hasta el almacenamiento o destinatario.
Mantener evidencia reproducible y auditable.
Facilitar la revisión humana legal, funcional y técnica.
Generar planes de remediación y seguimiento.
Repetir evaluaciones para detectar cambios.

Esta fase utilizará un navegador automatizado y datos sintéticos.

Chrome DevTools Protocol permite observar solicitudes, respuestas, encabezados, cuerpos y tiempos de red.

Niveles de evidencia
E0 — No observado
No se encontró evidencia en la cobertura ejecutada.
E1 — Evidencia estática
El dato aparece en HTML, JavaScript, código o documentación, pero no fue observado en ejecución.
E2 — Evidencia de captura
El dato fue ingresado, generado o almacenado en el navegador.
E3 — Evidencia de transmisión
El dato fue observado en una solicitud de red.
E4 — Evidencia de procesamiento
El dato aparece en lógica backend, integración, cola o servicio.
E5 — Evidencia de persistencia
El dato aparece en una base de datos, repositorio, archivo, log o respaldo.
La plataforma deberá evitar expresiones como“el sitio no captura el dato”cuando sólo corresponda decir:
“El dato no fue observado en las rutas y estados evaluados”.

16. Criterios de aceptación principales
CA-01. Campo personal visible
Dado un formulario con nombre, RUT, correo y teléfono, el sistema deberá:
Detectar los cuatro campos.
Clasificarlos correctamente.
Identificar cuáles son obligatorios.
Asociarlos al endpoint.
Capturar el texto informativo cercano.
Generar evidencia reproducible.
CA-02. Campo oculto
Dado un campo oculto con un identificador de usuario, deberá:
Detectarlo.
Clasificarlo.
Mostrar que no es visible.
Identificar cuándo se transmite.
CA-03. Tracking previo
Dado un sitio que ejecuta analítica antes del consentimiento, deberá:
Capturar la solicitud.
Identificar el dominio.
Asociarla al estado“sin interacción”.
Compararla con el estado“rechazar”.
Emitir un indicador de revisión.
CA-04. Rechazo efectivo
Dado un sitio que deshabilita correctamente el tracking al rechazar, deberá:
Mostrar la diferencia.
No generar un falso hallazgo de ejecución posterior.
Conservar evidencia de ambas sesiones.
CA-05. Política incompleta
Dado un dato observado que no aparece en la política, deberá:
Relacionar la evidencia técnica.
Mostrar la ausencia de coincidencia.
Indicar que puede existir información en otra fuente no analizada.
Solicitar revisión humana.
CA-06. Código fuente
Dado un endpoint que recibe un correo y lo guarda en una tabla:
Deberá identificar el DTO.
Identificar el controlador.
Identificar el servicio.
Identificar la entidad.
Construir el linaje.
Relacionarlo con el campo frontend cuando sea posible.
CA-07. Protección de evidencia
Dada una solicitud con contraseña o token:
El reporte no deberá mostrar el valor completo.
La evidencia deberá almacenarse cifrada o enmascarada.
El acceso deberá quedar auditado.

19. Recomendación de producto
La primera versión no debería intentar“leer toda la aplicación”ni resolver jurídicamente todos los casos.
El producto inicial debería especializarse en cuatro resultados confiables:
Qué datos solicita la interfaz.
Qué datos genera o almacena el navegador.
Qué datos transmite realmente la aplicación y hacia dónde.
Qué información o consentimiento se muestra antes de esa captura.
La capacidad más diferenciadora sería la comparación empírica entre estados:
Sin interactuarvs.Rechazarvs.Aceptarvs.Revocar
Esto permitiría pasar de una revisión meramente documental a una evaluación basada en evidencia técnica.
20. Definición final del producto
La plataforma deberá presentarse como:
Una herramienta de apoyo al levantamiento, diagnóstico y auditoría de tratamientos de datos personales en aplicaciones web, que combina observación externa, automatización de navegador, análisis de tráfico, revisión de políticas, análisis de código y construcción de trazabilidad, manteniendo evidencia verificable y revisión humana.
No deberá presentarse como:
Certificador automático de cumplimiento.
Sustituto de asesoría jurídica.
Herramienta de vigilancia de personas.
Escáner ofensivo.
Prueba concluyente de que un sitio cumple o incumple la ley.
Su valor estará en reducir drásticamente el trabajo manual necesario para descubrir y documentar la captura de datos, evidenciar discrepancias y orientar la revisión legal, funcional, de procesos y de ciberseguridad.
